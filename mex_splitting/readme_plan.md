# A plan for the policies README

The README is a guided tour, not a reference. Every section names one file to open and asks one question of it. The reader learns the vocabulary by meeting each word where it does work, in the order the work needs it. The reference material (every verb, every signature) lives in the type annotations and stays there.

## Outline

Each heading is one short section: a one-line user story, the file to open, what to look for, the one word learned. The story is the first thing in the section and it is the spec's first `describe` sentence, in the voice of whoever wants the behaviour. The spec is named, not quoted, so the README never carries a second copy of the story.

1. **One rule, one file.** *As a map maker, I want a region that does not check out to say why.* (`regions/spec/policies/check_spec.lua`.) Open `modules/regions/policies/check.lua`. A `Policy<C, T>` is a typed function from a context to a result, cut into named steps. Words: *policy*, *step*, *context*, *result*.
2. **Three ways to run a list of steps.** *As a map maker, I want every problem with my set of regions, not the first.* (`check_set_spec.lua`.) Stay in `check.lua`, then open `modules/regions/policies/check_set.lua`. Single stops at the first answer; Fold runs every step and threads the context; Product multiplies. Which one a policy is decides which verbs its steps may use. Words: *Single*, *Fold*, *Product*; *Unless/If*, *Answer*, *Refusal*, *Apply*, *Factor*.
3. **Steps are named so another file can find them.** *As the start module, I want to say what a start needs without regions knowing starts exist.* (`start/spec/policies/regions_spec.lua`.) Open `modules/start/policies/regions.lua`. Start adds its own rules to a policy regions owns, in front of a named step, only for its own region type. Words: *Contributes*, *When*, *Before/After*, *Replace/Remove*.
4. **The contract is what a module promises.** *As a module author, I want to ask regions what it offers and have the answer typed.* (`regions/spec/types_spec.lua`.) Open `modules/regions/types.lua` and the `Contract.X = X` lines at the foot of the policy files, each under `---@class (partial) RegionsContract`. A module's contract is the union of what its policy files declare by assignment; nobody writes it by hand, and because the field is declared where it is filled, Find All References on a policy's steps reaches every caller that asks the contract for it. `Policies.Contract(Modules.Regions)` is how a downstream file asks. Words: *contract*, *partial*.
5. **Facts are what a decision reads.** *As the start module, I want a team's start whether or not any module has set one.* (`start/spec/policies/facts_spec.lua`.) Open `modules/start/policies/facts.lua`. A Facts context is enriched by providers before any step runs; `Enrich` is the one place state enters. Words: *Facts*, *Provide*, *Enrich*, *PolicyContext*.
6. **A modoption is how the lobby reaches a policy.** *As a player, I want Easy Tax to mean the same thing in the lobby and in the match.* (`transfer/spec/modes/easy_tax_spec.lua`.) Follow one option through four files: `modules/transfer/modoptions.lua` declares `mex_splitting`; `modules/transfer/mode_dsl.lua` gives it a verb; `modules/transfer/modes/easy_tax.lua` claims it with that verb; `modules/transfer/policies/mex_splitting.lua` reads it off `ctx.modOptions`. A mode is a named bundle of claims on modoptions, written by the lobby and read by nobody in the match: by the time a policy runs, only the modoptions are left. Words: *modoption*, *mode*, *verb*, *claim*. This is the section to be honest in: the mode never meets the policy, so a reader who expects the mode to be a thing the match knows about will look for it and not find it. Say so.
7. **Evaluation is one call.** *As a module author, I want every module's steps to run as one policy, in the order they asked for.* (`spec/modules/module_handler_spec.lua`.) Open `modules/module_handler.lua` at `Evaluate`, and one caller: `modules/regions/api.lua` where `Check` runs. The loader assembles every module's contributions into one chain and runs it. Words: *Evaluate*, *loader*.
8. **The feature, end to end.** *As a player, I want my start's mex regions dealt round the players seated at it, nearest first.* (`transfer/spec/policies/mex_splitting_spec.lua`; this is the story in `mex_splitting.md`, verbatim.) Open `modules/transfer/policies/mex_regions.lua`, then `mex_splitting.lua` and `mex_splitting/claims.lua`. Regions → start → mex splitting is three modules, each extending the one below it, with no module reading another's state. No new words. This section is the proof the first seven were worth it.
9. **What is deliberately not here.** No story; this section has no behaviour. One paragraph: no inline policies, no hand-written contracts, no `Select`, no state on the context, no action registry (what a module does to the engine is a typed function on its `api_synced.lua`, domain validation first, so a caller can follow it). Each was tried; each is gone because it let a step mean something the type could not say.

## Why this shape

**Teach from the feature, not from the framework.** Every verb exists because a rule in regions, start or mex splitting needed it. Introducing the verb at the rule that needed it answers "why" at the moment "what" is shown. A README that lists verbs first is the reference, and the annotations already are the reference.

**One file per section.** The reader clicks, reads thirty lines, and comes back. Code in the README goes stale; a path and a question do not. When the file changes, the question still holds or the section is wrong, and that is visible.

**Order by dependency, not by discovery.** Your own path went policies → regions → start → mex splitting → back to policies to fix what you learned. Recording that path teaches the detours. The dependency order (a rule, how rules run, how files share rules, what a module promises, what a rule reads, where the lobby's choice enters, how it all runs, the feature) is the order the ideas need each other in, and it is the order a new module author will rebuild them in.

**Words are introduced once, where they work.** Nine sections, roughly twenty-five words, each attached to a line of code the reader has just looked at. The Flameink conversation is the case for this: every objection was a word met before its job.

**Section 9 is the defense.** The question a reviewer asks is "is all of this necessary." The honest answer is the list of what was removed and why. Writing that list keeps the README from defending things that should go next.

**The stories are the specs' first sentences, not a second corpus.** Each spec's first `describe` block already reads as the story (that was the rule when the specs were written). Putting that sentence at the top of the section, with the spec's path, is BDD at the cost of one line: the behaviour is stated, the proof is one click away, and when the spec changes the README is wrong in a way `grep` can find. Writing Given/When/Then in the README as well would be the ambitious version, and it would be the copy that goes stale. Keep the stories to one line; the spec is the scenario.

## What this is not

Not a changelog of the branch, not a place for examples that duplicate the code, not a reference for verb signatures. If a section needs more than a screen, it is two sections or it belongs in the types.
